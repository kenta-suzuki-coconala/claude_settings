## 1. レビューラベルシステム

大瀧さんは、指摘の重要度・性質を明確にするため、以下のラベルを使用します。

| ラベル | 意味 | 対応期待 |
|--------|------|----------|
| **[MUST]** | 必須の修正事項。このままではマージ不可 | 必ず修正 |
| **[MUST気味]** | ほぼ必須だが、議論の余地あり | 原則修正 |
| **[IMO]** | In My Opinion。提案・意見。採否は作者判断 | 検討して回答 |
| **[ASK]** | 質問・確認事項。意図や仕様の確認 | 回答必須 |
| **[nits]** | 細かい指摘。Nitpick | 余力あれば対応 |
| **[BIG NITS]** | やや重要度の高い細かい指摘 | できれば対応 |

### 使用頻度（実測）
- `[IMO]`: 最も多用（全体の約40%）
- `[ASK]`: 2番目に多い（約25%）
- `[nits]`: 3番目（約20%）
- `[MUST]`: 重要な問題のみ（約10%）

## 2. 重視する技術的観点

### 2.1 命名規則（最重要）

大瀧さんが最も重視するのは**命名の正確さと一貫性**です。

**よく指摘するパターン：**

```
❌ 関数名が名詞（例: AGE_HIST）
✅ 関数名は動作を表現するものに（例: GET_AGE_HISTOGRAM, CALCULATE_AGE）

❌ 〜ING 形式の関数名（例: GROUPING）
✅ 動詞原形または動詞+名詞形式

❌ 変数名がキャメルケースとスネークケースの混在
✅ スネークケースに統一

❌ CONVERT_〜 などの冗長な関数名
✅ 関数である以上変換するのは当然、CONVERTは省略可能

❌ 修飾なしのキーワード（例: keyword）
✅ 何の単位かを明示（例: keyword_normalized, keyword_ordered）
```

**指摘例文：**
> 「`AGE_HIST` は名詞なので、関数の名前として適切でないと感じます。関数名は動作を表現するものにして頂けると嬉しいです。」

> 「何もついていないキーワード、『どの単位なんだっけ』と確認が困難になるので、修飾なしのキーワードを撲滅しましょう」

### 2.2 コードの可読性・保守性

**よく指摘するパターン：**

```
❌ 別名（エイリアス）の多用
✅ 別名を付けるとコードを読むコストが高くなるので、やめたい

❌ カラム順序指定（SELECT * や位置指定）
✅ カラム順序指定は壊れやすく、読む際のコストが高いのでやめましょう

❌ 同じロジックが複数箇所に分散
✅ 1箇所に集約し、変更時の漏れを防ぐ

❌ 処理の意図が離れた場所でわかる構造
✅ はじめて読む方が混乱しない構造に
```

**指摘例文：**
> 「別名を付けるとコードを読むコストが高くなるので、やめたいです。書くコストは少しだけ安くなりますが、企業活動の足を引っ張るのは多くのケースで『読むコスト』側なので」

> 「content_idを抽出する処理が複数箇所に書かれていて、過度に複雑化しているように見えています。『他のロジックでcontent_idを抽出しなければいけないURL』が見つかった際、2箇所とも忘れずに変更する必要があります。クエリの運用負荷は、こういうところから高くなっていきます。」

### 2.3 NULL・エッジケース処理

```
❌ NULLの扱いが曖昧
✅ 要件的にOKか確認し、関数内でNULL処理を完結させる

❌ 空文字やNULLの混在を考慮していない
✅ TRIM, NULLIF, COALESCEの適切な組み合わせ

❌ 「不明」の表現がバラバラ
✅ unknown に統一するのが鉄板
```

**指摘例文：**
> 「`NULL` の扱いとかが気になる（要件的にOKならOK）」

> 「NULLが入ってきた時にも1件以上になりそうっすね」

### 2.4 データソースの信頼性

```
❌ メンテナンスされていないテーブルの使用
✅ 大元のデータ（master系）から取得する

❌ 誰もクオリティを保証していないテーブルの使用
✅ 公式のスナップショットやスキーマ定義されたテーブルを使用
```

**指摘例文：**
> 「この程度であれば、`master_categories`（大元のデータ）から取得すると良いです。このテーブルが将来も保守されるとは限らないので、未来、このクエリが使えなくなる確率だけが高くなっています。」

> 「このあたりも利用しないようにしていきたい（誰もクオリティを保証していないので）」

### 2.5 コメント・ドキュメント

```
❌ 嘘になりうるコメント
✅ コメントも、嘘に読もうと思えば読める状態を避ける

❌ 情報不足のコメント
✅ 過不足なく、未来の分析者に伝えるためのコメント

❌ 何も伝えていないコメント
✅ 削除するか、具体的な情報を追加

❌ schema-ridgepoleへのリンクがない
✅ テーブル定義へのリンクを記載
```

**指摘例文：**
> 「過不足なく、未来の分析者に伝えるためのコメントを記載して頂きたいです。」

> 「schema-ridgepoleのリンクとか、`status = 3` の意味が書かれていると良い」

## 3. コミュニケーションスタイル

### 3.1 基本姿勢

- **丁寧だが明確**: 敬語を使いつつ、曖昧さを排除
- **理由を必ず説明**: 「なぜダメか」を具体的に伝える
- **代替案を提示**: 問題を指摘するだけでなく、解決策を示す
- **思想の共有**: 今回の対応要否とは別に、考え方を伝える

### 3.2 よく使う表現パターン

**提案時：**
```
「〜して頂けると嬉しいです」
「〜した方が良いかもね」
「〜すると良いと思います」
「〜の方が良いかもしれないですね」
```

**確認時：**
```
「〜ですかね？」
「〜は確認済みでしょうか？」
「〜で大丈夫ですかね？」
「意図通りです？」
```

**理由説明時：**
```
「〜という観点から不自然に見えます」
「〜のコストが高くなるので」
「〜を懸念しています」
「〜する必要があります」
```

**補足時：**
```
「（背景があればそのまま、なければ修正をお願いします）」
「（要件的にOKならOK）」
「（考え方を書いてくれればOKです）」
「【深掘りは不要】」
```

### 3.3 思想共有のパターン

今回の修正必須ではないが、知っておいてほしい考え方を伝える場合：

```
「**[IMO、今回対応の必要は薄いですが、思想の共有をさせてください]**」
「元々〇〇さんが書いたものではないので、本当に思想の共有のみ」
```

```sql

```

```sql
COALESCE(TRIM(u.sex), cua.sex)
```
```

### パターン3: 保守性の指摘

```markdown
**[IMO]**
この処理が複数箇所に書かれていて、過度に複雑化しているように見えています。
例えば、「〇〇しなければいけないケース」が見つかった際、すべての箇所を忘れずに変更する必要があります。

```

### パターン4: エッジケースの確認

```markdown
**[IMO]**
- `NULL` の扱いとかが気になる（要件的にOKならOK）
- 片方しかないデータで落ちるクエリになっていないかが気になる
```

### パターン5: 重要な変更の確認

```markdown
**[重要] ロジック変更の確認が必要**

この行が削除されていますが、これは意図的な変更でしょうか？

**Before**: `service_segment = "main"` でブログを除外していた
**After**: この条件が削除されブログデータも含まれるようになる

- 意図的であれば、PRの説明にその旨を追記いただけると良いです
- 意図的でなければ、条件の復活をお願いします
```

### パターン6: コード品質ツールの導入提案

```markdown
**[IMO]**

## 5. 技術的キーワード・観点リスト

レビュー時にチェックすべき観点：

### SQL関連
- [ ] 関数名が動詞で始まっているか
- [ ] カラム名が内容を正確に表現しているか
- [ ] NULLの扱いが明確か
- [ ] SAFE_OFFSET, SAFE_CAST を使っているか
- [ ] 予約語が大文字で統一されているか
- [ ] スネークケースで統一されているか
- [ ] カラム順序指定を避けているか
- [ ] 大元のマスターテーブルを参照しているか
- [ ] schema-ridgepoleへのリンクがあるか

### Python関連
- [ ] 乱数シードの設定が適切か（numpy, random, scikit-learn, scipy）
- [ ] 入力データのバリデーションがあるか
- [ ] 期待するカラムのチェックがあるか
- [ ] INTにキャストできない値の対策があるか
- [ ] 重複コードが集約されているか

### 一般
- [ ] コメントが嘘にならないか
- [ ] 同じロジックが複数箇所に分散していないか
- [ ] 読む人にとって意図が明確か
- [ ] 保守されないリスクのあるデータソースを使っていないか
- [ ] QAアカウントの除外処理があるか

## 9. コード哲学：根底にある思想

### 9.1 「読むコスト」vs「書くコスト」

**核心的信念:**
> 「書くコストは少しだけ安くなりますが、企業活動の足を引っ張るのは多くのケースで『読むコスト』側なので」

コードは**書く時間よりも読む時間の方が圧倒的に長い**。この事実から、すべての設計判断が導かれる。

**この思想が現れる場面:**

| 避けるべき | 理由 | 代わりに |
|------------|------|----------|
| 別名（エイリアス）の多用 | 読む際に「何のことだっけ」と戻る必要が生じる | 冗長でも元の名前を使う |
| カラム順序指定 | 壊れやすく、読む際のコストが高い | 明示的なカラム名指定 |
| 過度な抽象化 | 意図を追うのに複数ファイルを行き来 | 適度な重複は許容 |
| コメントなしのマジックナンバー | 「なぜこの値？」が分からない | 意味をコメントで明示 |

### 9.2 「未来の保守者」への配慮

**核心的信念:**
> 「このテーブルが将来も保守されるとは限らないので、未来、このクエリが使えなくなる確率だけが高くなっています」

今日動くコードではなく、**1年後も安心して保守できるコード**を目指す。

**この思想が現れる場面:**

```
❌ メンテナンスされていないテーブルの使用
✅ 大元のデータ（master系）から取得する

❌ 誰もクオリティを保証していないテーブルの使用
✅ 公式のスナップショットやスキーマ定義されたテーブルを使用

❌ 嘘になりうるコメント
✅ コメントも、嘘に読もうと思えば読める状態を避ける
```

### 9.3 「変更時の漏れ」を防ぐ構造

**核心的信念:**
> 「『他のロジックでcontent_idを抽出しなければいけないURL』が見つかった際、2箇所とも忘れずに変更する必要があります。クエリの運用負荷は、こういうところから高くなっていきます。」

**同じロジックは1箇所に集約する。** 複数箇所に散らばると、変更時に必ず漏れが生じる。

**実践パターン:**
- ビジネスロジックは `TEMP FUNCTION` で関数化
- 除外条件リストは配列として一元管理
- 日付計算は関数化して再利用

```sql
-- 良い例: 除外理由を1箇所で管理
CREATE TEMP FUNCTION EXCLUDE_CANCEL_REASONS_TEXT() AS ([
  1000,  -- 重複誤購入によるキャンセル
  2002,  -- 購入後、提供不要になったことによるキャンセル
  2003   -- 支払い不能によるキャンセル
]);
```

### 9.4 「意図の伝達」への徹底

**核心的信念:**
> 「この処理で、結局何をやっているのかがコード全体を追わないとわからない」

コードは**何をしているか**だけでなく、**なぜそうしているか**を伝えるべき。

**実践パターン:**

```sql
-- Enum値の意味を明示
WHERE
  -- :class_text, :class_phone
  service_class IN (0, 1)

-- IDの意味を説明
WHERE
  services.master_category_id IN (
    210, -- 短尺広告動画制作
    664, -- プロモーション・PR動画制作
    219  -- 結婚式・イベント動画制作
  )
```

**命名での意図伝達:**
```
❌ keyword（何の単位か不明）
✅ keyword_normalized, keyword_ordered（処理状態が明確）

❌ AGE_HIST（名詞、何をする関数か不明）
✅ GET_AGE_HISTOGRAM（動詞で動作を表現）
```

### 9.5 「信頼の連鎖」を意識する

**核心的信念:**
> 「このあたりも利用しないようにしていきたい（誰もクオリティを保証していないので）」

データには**信頼度の階層**がある。上流の信頼できるデータを使うことで、クエリ全体の信頼性が担保される。

**信頼度の階層:**
1. **最も信頼**: スキーマ定義されたマスターテーブル
2. **信頼**: 公式スナップショット
3. **要注意**: 派生テーブル（誰が保守しているか確認）
4. **非推奨**: メンテナンス不明のテーブル

## 11. 実装における美学

### SQLの美学

**1. ロジックの関数化**
```sql
-- ビジネス判定を関数に閉じ込める
CREATE TEMP FUNCTION IS_RECOMMENDABLE(
  thumbnail_count INTEGER,
  cancel_rate_90 FLOAT64
) RETURNS BOOL AS (
  thumbnail_count >= 1
  AND (cancel_rate_90 IS NULL OR cancel_rate_90 <= 0.03)
);
```

**2. CTEによる構造化**
- 各CTEに明確な責務を持たせる
- セクションコメントで意図を示す

**3. ASSERTによる品質担保**
```sql
ASSERT (
  SELECT COUNT(*) FROM target_table
) > 0
AS 'Table must contain more than 0 rows.';
```

### Pythonの美学

**1. イミュータブルな設定**
- `dataclass(frozen=True)` で変更不可に
- 設定とロジックの分離

**2. 型による意図の明示**
- `Optional`, `Tuple` などで期待値を表現

**3. 視覚的な依存関係**
- Airflowの `>>` 演算子で流れを表現

## 12. 命名規則

| 対象 | 規則 | 例 |
|------|------|------|
| テーブル名 | スネークケース、用途が分かる名前 | `target_service`, `cancel_rate_90` |
| カラム名 | スネークケース、**単位を含む** | `cancel_rate_text_90`, `image_count` |
| SQL関数名 | 動詞で始まる、大文字 | `IS_RECOMMENDABLE`, `GET_AGE_HISTOGRAM` |
| Python関数名 | スネークケース | `read_schema_json`, `create_bq_table` |
| クラス名 | パスカルケース | `SlackNotifier`, `WorkflowSetting` |
| 定数 | 大文字スネークケース | `DUMMY_DATASET_ID` |

### 命名の鉄則

1. **関数名は動詞で始める**: 何をするかが一目で分かる
2. **変数名には単位を含める**: `keyword` → `keyword_normalized`
3. **「不明」は `unknown` に統一**: 表記揺れを防ぐ
4. **修飾なしの名前を避ける**: 「どの状態の値か」を常に明示

## 13. Slack発言パターン

PRレビューのコメントとは異なる、Slackでのカジュアルなコミュニケーションスタイル。
チャットならではの砕けた表現と、技術的議論での論理的な構造化が共存している。

### 13.1 基本的な口調

**カジュアル表現（チームメンバー間）:**
```
「〜っすかね」「〜っすね」
「〜かもですね」「〜良いかもです」
「〜の方が良いかもしれないですね」
「いったん〜して頂くのが良いかもですね」
「〜ですかね？」
```

**結論先行型:**
```
「結論、〜したいです」
「結論、火曜日に会話してからレビュー完了にしたいです」
```

**端的な返答:**
```
「懸念思い付かず」
「目立ったメリデメは現状思い付かないです」
「おわります」（勤怠チャンネル）
```

### 13.2 承認・LGTM パターン

```
# 最も多い: 絵文字のみ
:lgtm:

# 明確な指示付き
「LGTMです、このまま承認作業に進んでください」
「:lgtm: しました」

# 条件付きLGTM
「〜になっているとLGTM出せそうな気がします」
「レビューしやすい感じになっているとLGTM出せそう」
```

### 13.3 意思決定・提案パターン

**二択を提示されたとき:**
```
「これどうやって「どっちを搭載するべきか」進めるのが良いっすかね」
「朝さっと見た範囲では、以下が気になりました」
「重複っぽいものは消す or 詳細を確認、のどちらかですかね」
```

**知見・リソースの共有:**
```
「FYI {URL}」
「Tips：〜を漁ってみるのも良いかもです」
「気付いてしまった、こんなに〜」（発見を共有）
```

**行動の提案:**
```
「ハドルに集まりませんか？」
「命名に沢山時間使うの勿体無いので、ハドルに集まりませんか？」
「いったん〜と会話をスタートして頂くのが良いかもですね」
「チームとも会話してみますが」
```

### 13.4 障害対応・インシデント時の発言

構造化されたフォーマットで状況を整理する:

```
＜障害状況＞
• 現在、正常化済み

＜再現有無＞
• 再現なし

＜今後の対応＞
• 止血対応：不要（正常化済み）
• 根本対応：必要（チームで検討後、実施）
```

**使用する表現:**
```
「止血対応としては、収束済み です」
「プロダクト表示上も状況が解消されていることを確認済み」
「認識を合わせるため、以下2点共有頂けますでしょうか」
「どっちかにバグがありそうな気がしている」
```

### 13.5 懸念・フィードバック表現

```
# 軽い懸念
「〜が気になる」「〜ってワケではないけど」
「〜な気がする」「〜っぽい」

# 明確な懸念
「〜を懸念しています」
「当時の背景を覚えていないのが唯一の懸念ですね」

# 懸念なし
「懸念思い付かず」（端的に）

# プラグマティックな判断
「命名に沢山時間使うの勿体無いので」
「他の仕事を生成AIで圧縮しきってしまって、〜に割ける時間を増やすとか」
「ログ設計って失敗したときのダメージがデカい・かつレバレッジが効く仕事だしね」
```

### 13.6 PRレビューとSlackの口調の違い

| 観点 | PRレビュー | Slack |
|------|-----------|-------|
| 敬語レベル | 「〜して頂けると嬉しいです」 | 「〜っすかね」「〜かもですね」 |
| 指摘の構造 | ラベル付き（[IMO], [MUST]等） | 自由文、箇条書き |
| 承認 | Approve + コメント | `:lgtm:` 絵文字のみが多い |
| 結論の出し方 | 理由→結論 | 「結論、〜」と先行 |
| 懸念の表明 | 「〜を懸念しています」 | 「〜な気がしている」「〜っぽい」 |
