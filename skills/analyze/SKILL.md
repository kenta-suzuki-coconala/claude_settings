# /analyze - ココナラ分析実行

ココナラの分析依頼を受け取り、用語解釈・情報収集・クエリ生成・実行・考察までを一貫して行います。

## 使い方

```bash
/analyze 昨日、イラストで検索した人数は？
/analyze 直近7日間の購入ファネルを分析して
/analyze ordersテーブルのステータス別件数
```

## 処理内容

1. **用語解釈**: ユーザー表現をシステム表現に変換
2. **情報収集**: 用語集にない情報は schema-ridgepole / bq で調査
3. **知識の蓄積**: 調査結果を learned-knowledge.md に追記
4. **クエリ生成**: 分析目的に適したSQLを作成
5. **データサイズ確認**: `--dry_run` で事前チェック（100円超は確認）
6. **クエリ実行**: BigQueryでクエリを実行
7. **数値検証**: 結果の規模感をベンチマークと比較して妥当性確認
8. **考察・レポート**: 結果の解釈とビジネス示唆を提供

#### Step 0: 初期要件確認（複雑な集計の場合）

**複雑なクエリを作成する前に、以下の要件を確認してください。**

これにより、後から「やっぱり〇〇も除外して」「△△の定義が違う」といった手戻りを削減できます。

**確認チェックリスト**:

| 項目 | 確認内容 | 例 |
|------|----------|-----|
| **出力項目の定義** | 各指標の具体的な定義は明確か？ | 「登録者数」→「出品かつ売上のあるユーザー数」 |
| **除外条件** | 除外すべきデータはあるか？ | 見積もりサービス（service_class=2）、except_users |
| **データ品質** | 異常値・NULL値の扱いは？ | 都道府県: NULL→'未登録'、'Toky'→'その他' |
| **集計期間** | 期間は明確か？関数化するか？ | FROM_DATE(), TO_DATE()で管理 |
| **計算単位** | 単位は明確か？ | 円/人、件/日、率 |

**AskUserQuestion での確認例**:

複雑な集計を依頼された場合、以下のような確認を行います：

```
このクエリを作成する前に、いくつか確認させてください：

1. **出力指標の定義**
   - 「アクティブユーザー」の定義は何ですか？
     - 期間内に流通高がある出品者？
     - 期間内にログインした出品者？

2. **除外条件**
   - 見積もりサービス（service_class=2）は除外しますか？
   - except_usersリストのユーザーは除外しますか？

3. **データの正規化**
   - 都道府県のNULL値や異常値はどう扱いますか？

4. **集計期間**
   - 期間: 2025-12-01 〜 2025-12-31 でよいですか？
```

**スキップしてよい場合**:
- 単純なクエリ（単一テーブルの集計等）
- 既存クエリの微修正
- ユーザーが詳細な仕様を既に提示している場合

#### Step 1: 用語解釈 & 情報収集

**1-1. ローカルリソースを確認**
```
1. .claude/resources/ubiquitous-dict/aliases.md を読み込む
2. .claude/resources/coconala/learned-knowledge.md から関連知識を検索する
   - Grep ツールで、ユーザーの分析要望に含まれるキーワード（テーブル名、カラム名、ドメイン用語）を検索
   - ヒットしたセクションを Read ツール（offset/limit 指定）で読み込む
   - 該当がなければスキップして Step 1-2 へ進む
3. .claude/resources/coconala/user-action-guide.md で関連アクションを特定
4. （KPI分析の場合）.claude/resources/coconala/kpi/README.md で検証済みクエリを検索
```

**1-2. 情報が不足している場合 → 外部ソースを調査**

schema-ridgepole（DBスキーマ）:
```bash
# テーブル一覧を検索
gh api repos/welself/schema-ridgepole/contents/projects/coconala --jq '.[].name' | grep -i "{検索語}"

# スキーマ詳細を取得
gh api repos/welself/schema-ridgepole/contents/projects/coconala/{テーブル名}.schema --jq '.content' | base64 -d
```

BigQuery（BQスキーマ）:
```bash
# テーブルスキーマを確認
bq show --schema --format=prettyjson {dataset}.{table}

# テーブル一覧
bq ls {dataset}
```

**1-3. 調査結果を追記**

新しい情報を得た場合は、Edit ツールで `.claude/resources/coconala/learned-knowledge.md` に追記してください。

#### Step 5: 数値検証（必須）

**レポート出力前に、結果の規模感を検証します。**

**5-1. ベンチマーク参照**
```
.claude/resources/coconala/sanity-check-benchmarks.md を読み込む
```

**5-2. 検証クエリの実行**

分析対象に応じた簡易クエリを実行して全体規模を確認：

| 分析対象 | 確認指標 | 日次目安 |
|----------|----------|----------|
| 流通高・売上 | 日次GMV | 4,000〜5,000万円 |
| ユーザー数 | DAU | 数十万〜100万 |
| 検索 | 日次検索数（初回） | 数十万件 |
| 購入 | 日次購入件数 | 数千〜1万件 |

**5-3. 判定**

| 状況 | 対応 |
|------|------|
| ベンチマーク範囲内 | OK → Step 6へ |
| ベンチマークの10%未満 | フィルタ条件を確認、意図的なら理由を記載 |
| ベンチマークの10倍以上 | 重複カウント・フィルタ漏れを確認 |
| 明らかに異常 | クエリを見直し、必要ならユーザーに確認 |

```

## 知識のコントリビュート（推奨）

### Step 7: 新しい知識の共有を促す

**分析中に新しい知識を得た場合**、レポート出力後にユーザーへコントリビュートを提案してください。

#### 提案すべきケース

| ケース | 例 |
|--------|-----|
| 新しいテーブル/カラムの発見 | `orders_dates` テーブルの構造を調査した |
| ステータス値の定義 | `talkroom.status = 3` が「クローズ」を意味すると判明 |
| 分析用語の定義 | 「新規ユーザー」の判定ロジックを確認した |
| 有用なクエリパターン | 特定の分析でよく使うJOINパターンを発見 |

#### 提案メッセージ例

レポート出力後、以下のように提案：

```markdown
---

**コントリビュートの提案**

今回の分析で新しい知識を得ました。チーム全体で共有するため、
PRの作成をお勧めします。

**追加した知識**:
- {知識の概要}

**コマンド例**:
```bash
git checkout -b knowledge/{トピック名}
git add .claude/resources/coconala/learned-knowledge.md
git commit -m "knowledge: {追加した知識の概要}"
git push -u origin knowledge/{トピック名}
gh pr create --title "knowledge: {概要}" --body "## 追加した知識\n\n- {内容}"
```

PRを作成しますか？
```

#### AskUserQuestion での確認

新しい知識を追記した場合、AskUserQuestion で確認：

```
今回の分析で以下の知識を learned-knowledge.md に追記しました：
- {知識の概要}

この知識をPRとしてリポジトリに共有しますか？

選択肢：
1. PRを作成する（推奨）
2. 今回はスキップ
```

ユーザーが「PRを作成する」を選択した場合、ブランチ作成からPR作成までを実行してください。

## 深掘り分析の提案（必須）

### Step 8: 次の分析ステップを提案する

**レポート出力後、必ずユーザーに深掘り分析の選択肢を提示してください。**

分析は1回で終わりではなく、インサイトを得るためには複数の視点からの深掘りが重要です。
ユーザーが次のアクションを取りやすいよう、具体的な選択肢を**5つ**提示します。

#### 提示タイミング

- Step 6（レポート出力）完了後
- Step 7（知識コントリビュート）の確認後

#### 選択肢の設計方針

以下の5つのカテゴリから、分析内容に応じた選択肢を提示：

| カテゴリ | 説明 | 例 |
|----------|------|-----|
| **1. セグメント分解** | 既存の分析をさらに細分化 | デバイス別、新規/既存別、カテゴリ別 |
| **2. 時系列深掘り** | 時間軸での変化を分析 | 時間帯別、曜日別、トレンド分析 |
| **3. 離脱・課題の特定** | ボトルネックや問題点を深掘り | 離脱ポイント分析、0件ヒット分析 |
| **4. 比較分析** | 異なるグループ間の比較 | 購入者vs未購入者、高単価vs低単価 |
| **5. 生データ確認** | 実際のユーザー行動を確認 | サンプルユーザーのジャーニー表示 |

#### AskUserQuestion での提示

**必ず AskUserQuestion ツールを使用して選択肢を提示してください。**

選択肢は最大4つまでしか設定できないため、5つ目は「その他」として自由入力を促します。

```
この分析をさらに深掘りするために、どの方向で分析を進めますか？

選択肢：
1. {セグメント分解の具体的な提案}
2. {時系列深掘りの具体的な提案}
3. {離脱・課題特定の具体的な提案}
4. {生データ確認の具体的な提案}

※「その他」を選択すると、別の分析軸や追加の質問を自由に入力できます
```

#### 分析タイプ別の選択肢例

**ファネル分析の場合**:
```
1. デバイス別に分解 - PC/スマホWeb/アプリで転換率に差があるか確認
2. 新規/既存ユーザー別に分解 - 初回訪問者と既存会員で行動パターンが異なるか確認
3. 離脱ポイントの深掘り - 検索したが詳細を見なかったユーザーの行動を分析
4. 生データのサンプル表示 - 購入者・未購入者それぞれのセッション行動ログを時系列で表示
```

**KPI分析（GMV等）の場合**:
```
1. カテゴリ別に分解 - 主要カテゴリごとのGMV内訳を確認
2. 時間帯別の傾向 - 購入が集中する時間帯を特定
3. 単価帯別に分解 - 高単価/低単価取引の構成比を確認
4. 新規/既存の内訳 - 新規ユーザーと既存ユーザーのGMV貢献度を比較
```

**検索分析の場合**:
```
1. デバイス別の検索傾向 - PC/スマホで検索キーワードに違いがあるか
2. 検索→クリックの紐付け - どのキーワードがどのサービスに繋がっているか
3. 0件ヒット分析 - 検索結果が0件だったキーワードを特定
4. 検索キーワードのサンプル表示 - 購入に繋がった/繋がらなかったキーワードを比較
```

#### 選択後の対応

ユーザーが選択肢を選んだ場合：
1. 選択された分析を即座に実行
2. 結果をレポート形式で出力
3. さらなる深掘り選択肢を再度提示（必要に応じて）

**深掘りのループ**: ユーザーが「終了」や「完了」を選ぶまで、分析→提案→分析のサイクルを継続します。

#### 提示時の注意点

- 分析内容に**具体的に関連した**選択肢を提示する（汎用的すぎる選択肢は避ける）
- 各選択肢には**何がわかるか**を簡潔に説明する
- 技術的に実現可能な選択肢のみを提示する（データがない分析は提案しない）
- ユーザーの目的（課題発見、施策検討など）を意識した選択肢を優先する
