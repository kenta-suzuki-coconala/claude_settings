# /notion-project-doc - 施策資料作成

施策設計書を起点に、技術調査→検討資料をまとめて作成します。

## 使い方

```
/notion-project-doc                        # 対話形式で作成
/notion-project-doc ESのバージョンアップ      # 施策名を指定して作成
```

---

## 重要なルール

**Notion へのページ作成（`API-post-page`）は、ユーザーが明示的に「OK」「はい」「進めて」等の承認を返すまで絶対に実行しない。**
ドラフトを提示して AskUserQuestion で確認し、ユーザーの承認メッセージを受け取ってから Step 4 以降に進むこと。

---

## 実行手順

### Step 1: ワークスペース構造の読み込み

```
Read .claude/resources/notion/workspace-structure.md
```

### Step 2: 基本情報の収集

以下をユーザーから収集する（未提供の場合は AskUserQuestion で確認）：

- **施策名**：FY2026 DB エントリ名に使用
- **チーム**：workspace-structure.md の正規名一覧を参照
- **施策の概要**：何を実現したいか（1〜3文程度で可）

> 詳細な施策内容は Step 3 の技術調査結果を踏まえて作成するため、この時点では概要のみで良い。

### Step 3: 技術調査（dt-system-question）

施策名・概要をもとに、`dt-system-question` スキルを使って技術調査を実施する。

```
Skill: dt-system-question
調査内容の例：
  - 現状の実装・構成（現在のバージョン、アーキテクチャ等）
  - 施策を実現するために必要な変更・作業
  - 影響範囲（依存するコンポーネント・サービス）
  - リスク・注意点
  - 実施ステップの候補
```

調査結果を以下に活用する：

| 成果物 | 記載内容 | 読者 |
|--------|----------|------|
| 施策設計書（Step 4） | 背景・目的、現状と課題（表）、実施内容・影響範囲・リスクの要点のみ | マネージャー |
| 検討資料（Step 5） | 課題ごとの技術的詳細（廃止機能・修正箇所・調査結果等） | 実装担当者 |

> **施策設計書には技術的な詳細を書かない。** 何が課題で何をするかが明確に伝わればよい。技術詳細は検討資料に記載する。

調査結果から**課題の一覧**を整理する（後で検討資料の単位になる）。例：
- 課題A: アナライザプラグインの非互換
- 課題B: クライアントライブラリの更新
- 課題C: コード修正（廃止 API 対応）

### Step 3.5: ドラフト確認

Step 3 の調査結果をもとに、施策設計書のドラフトをユーザーに提示して確認を取る。

以下の形式でドラフトを出力する（**技術的詳細は含めない**）：

```
---【施策設計書 ドラフト】---

タイトル: <施策名>

## 背景・目的
<なぜこの施策が必要か（背景）と、何を達成するか（目的）を2〜3文で>

## ロードマップ
<施策全体の進め方をステップで列挙（番号付きリスト）。大きな流れが伝わればよい>
1. <ステップ1>
2. <ステップ2>
...

## 現状と課題
※「空・雨・傘」で整理: 空=事実、雨=解釈（なぜ問題か）、傘=対策（対応方針に対応）
| 観点 | 現状 | 課題 | 対応方針 | 検討資料 |
|------|------|------|----------|----------|
| <観点1> | <現状の事実> | <それが問題である理由> | <対策の要点> | <対応する検討資料名> |
| <観点2> | <現状の事実> | <それが問題である理由> | <対策の要点> | <対応する検討資料名> |
...

## 影響範囲
<影響するシステム・サービス名のみ。詳細は検討資料へ>

## リスク・注意点
<プロジェクト遂行上のリスクのみ。実装レベルの技術的リスクは検討資料へ>
---

【検討資料の候補（課題ごと）】
- <課題A名>: <概要>
- <課題B名>: <概要>
...
```

AskUserQuestion で確認：「このドラフトで Notion に作成しますか？修正があればお知らせください。」

- 修正がある場合はドラフトを更新し、再度確認する
- **ユーザーが明示的に承認するまで Step 4 に進んではならない（「OK」「はい」「進めて」等の返答を待つ）**
- 承認なしに `API-post-page` を呼び出すことは禁止

### Step 4: 施策設計書の作成（FY2026 DB）

**前提: Step 3.5 でユーザーの明示的な承認を得ていること。**

```
mcp__notionApi__API-post-page で作成：
  parent: { database_id: "26822641-b4a4-8014-83b0-d57da4e85d7f" }
  properties:
    ドキュメント名: { title: [{ text: { content: "<施策名>" } }] }
    チーム: { multi_select: [{ name: "<FY2026用チーム名>" }] }
    カテゴリー: { multi_select: [{ name: "施策資料" }] }
```

> **注意：** FY2026 DB のタイトルプロパティ名は `ドキュメント名`。`title` や `名前` では validation_error になる。
>
> **カテゴリーについて：** 施策設計書には通常 `施策資料` を使用する。既存値：`施策資料` / `設計書` / `提案` / `計画中` / `DesignDoc`

作成後、`mcp__notionApi__API-patch-block-children` で以下の構成で本文を追加：

```
heading_2: "背景・目的"
paragraph: "（背景と目的を2〜3文で。技術詳細は含めない）"
heading_2: "ロードマップ"
numbered_list_item: "（施策全体の進め方をステップで列挙）"
heading_2: "現状と課題"
table: （観点 / 現状 / 課題 / 対応方針 / 検討資料 の5列テーブル）
  ※空・雨・傘の考え方で整理すること（ドキュメントには書かない）
  ※「検討資料」列には対応する検討資料名を記載（Step 5 作成後にリンク化する）
heading_2: "影響範囲"
bulleted_list_item: "（影響するシステム・サービス名のみ）"
heading_2: "リスク・注意点"
bulleted_list_item: "（プロジェクト遂行上のリスクのみ）"
heading_2: "検討資料"
bulleted_list_item: "（Step 5 で作成した各検討資料へのリンクを追加。この時点では空でよい）"
```

> **施策設計書の記載原則:**
> - マネージャーが読むドキュメント。技術的な詳細（コードパス・API名・gem バージョン等）は書かない
> - 「何が問題で（現状と課題）」「何をするか（実施内容）」「どんなリスクがあるか」が伝わればよい
> - 技術的詳細は検討資料（Step 5）に委ねる
> - **文章を paragraph ブロックに記載する際は、1文ごとに別の paragraph ブロックとして分けること**

**図表の活用（推奨）：** 内容に応じて以下を積極的に使うこと。

| 使用場面 | ブロック型 | 指定方法 |
|----------|-----------|---------|
| アーキテクチャ・データフロー・状態遷移 | `code` | `language: "mermaid"` |
| 比較・一覧（バージョン差分・プロパティ一覧等） | `table` | `table_width`, `has_column_header: true`, `children: [table_row...]` |

> チーム名は DB ごとに異なる。workspace-structure.md の「グループ（チーム）について」テーブルを参照して FY2026 列の値を使用すること。

### Step 5: 検討資料の作成（課題ごとに個別作成）

Step 3 で整理した**課題ごとに1つずつ**検討資料を作成する。

AskUserQuestion で確認：
「以下の課題ごとに検討資料を作成しますか？不要なものがあれば除外してください。」
（Step 3.5 のドラフトに記載した【検討資料の候補】をリスト表示する）

確定した課題リストの各課題について、以下を繰り返す：

#### 各検討資料の作成

```
mcp__notionApi__API-post-page で作成：
  parent: { database_id: "26522641-b4a4-80bc-a62d-dd3352a0572f" }
  properties:
    ドキュメント名: { title: [{ text: { content: "<施策名>_<課題名>" } }] }
    チーム: { multi_select: [{ name: "<資料置き場用チーム名>" }] }
    カテゴリー: { multi_select: [{ name: "<カテゴリー>" }] }
```

> **注意：** 資料置き場 DB のタイトルプロパティ名は `ドキュメント名`。
>
> **カテゴリーの選び方：** 既存値から最も近いものを選ぶ。検討資料は基本的に `技術調査` を使用する。
> 既存値：`技術調査` / `定常業務` / `引き継ぎ` / `戦略ドキュメント` / `計画中` / `チームビルディング`

作成後、`mcp__notionApi__API-patch-block-children` で本文を追加。

**冒頭は必ず**施策設計書へのリンク（`paragraph: "🔗 施策設計書: <リンク>"`）。

本文の構成は課題の性質に応じて柔軟に決めてよい。以下に2つの典型パターンを示す：

**パターンA: 選択肢比較型**（バージョン選定・方式比較など、複数案を比較する場合）
```
paragraph: "🔗 施策設計書: <施策設計書へのリンク>"
heading_2: "概要・目的"
paragraph: "（この検討資料が扱う課題の概要）"
heading_2: "方針（案）"
paragraph: "（推奨する方針を端的に）"
  heading_3: "理由"
  bulleted_list_item: "..."
  heading_3: "懸念点"  ← 必要に応じて
  bulleted_list_item: "..."
heading_2: "<選択肢の比較セクション名>"  ← 例: "8.x vs 9.x 比較"、"方式の比較"
table: （比較表。行ヘッダーありの場合は has_row_header: true）
  heading_3: "<補足サブセクション>"  ← 必要に応じて複数の h3 で詳細を整理
  table / bulleted_list_item: "..."
heading_2: "補足" or "現状の詳細"  ← 必要に応じて
paragraph / table / bulleted_list_item: "（参考情報・詳細データ）"
heading_2: "注意点・残課題"
bulleted_list_item: "..."
```

**パターンB: 調査・修正型**（コード修正箇所の洗い出し・技術調査など）
```
paragraph: "🔗 施策設計書: <施策設計書へのリンク>"
heading_2: "概要・目的"
paragraph: "（この検討資料が扱う課題の概要）"
heading_2: "現状の詳細"
table: "（現状の構成・バージョン等を表で整理）"
heading_2: "修正箇所" or "検討・調査内容"
table: "（修正対象の一覧。リポジトリ/ファイル/内容/対応 等の列）"
heading_2: "方針・結論"
paragraph / bulleted_list_item: "（この課題に対する対応方針。未確定なら TBD と明記）"
heading_2: "注意点・残課題"
bulleted_list_item: "..."
```

> **パターン選択の指針:** 複数の選択肢を比較する課題は A、既存コードの調査・修正箇所の洗い出しは B を使う。
> いずれのパターンでも、h3 サブセクションは必要に応じて自由に追加してよい。

**文章の記載ルール：** paragraph ブロックに文章を書く際は、**1文ごとに別の paragraph ブロックとして分けること**。

**図表の活用（推奨）：** バージョン差分・修正箇所の比較は `table`、処理フロー・依存関係は Mermaid（`code` + `language: "mermaid"`）を積極的に使うこと。比較表は `has_row_header: true` を活用して見やすくする。

#### 双方向リンクの設定

全検討資料の作成後：
- 施策設計書の「検討資料」セクション → 各検討資料へのリンクを bulleted_list_item で追加（`mcp__notionApi__API-patch-block-children`）
- 施策設計書の「現状と課題」テーブル → 検討資料列の該当セルにもリンクを設定（可能であれば）
- 各検討資料の冒頭 → 施策設計書へのリンク（作成時に paragraph ブロックで追加済み）

### Step 6: 結果報告

作成したページの URL を一覧で報告する：

```
✅ 作成完了

📄 施策設計書: <URL>（FY2026 DB）
📦 検討資料:
  ├── <課題名A>: <URL>（資料置き場 DB）
  ├── <課題名B>: <URL>（資料置き場 DB）
  └── ...
```
