# /review-log - ログ出力チケットレビュー

Notionに記載されたログ出力内容（user_action_raw / user_log_raw の追加・変更・削除）をレビューします。

## 使い方

```bash
/review-log <NotionチケットURL>
/review-log https://www.notion.so/1-7ac22641b4a482ed9cec018dd6423064
```

## 前提条件

- 環境変数 `NOTION_API_KEY` が設定されていること
  - `~/.claude/settings.json` の `env` または `~/.zshrc` 等で export
- 対象のNotionページにIntegrationが接続されていること
  - ページ右上「...」→「コネクトを追加」からIntegrationを追加する
  - **APIアクセスで404エラーが出た場合**: Integrationがページに接続されていない可能性が高い。ユーザーに以下を案内する:
    1. 対象のNotionページを開く
    2. 右上の「...」→「コネクトを追加」をクリック
    3. `NOTION_API_KEY` に対応するIntegration名を選択して接続
    4. 再度レビューを実行
- `gcloud auth application-default login` で GCP 認証済みであること
  - Google Sheets API によるuser_action仕様書の取得に使用
  - GCPプロジェクト: `indigo-medium-816`

## 処理フロー

### Step 1: チケット読み込み

1. Notion APIでチケットのページ内容を取得する
   - 認証: `Authorization: Bearer $NOTION_API_KEY`、`Notion-Version: 2022-06-28`
   - ページID抽出 → `/v1/blocks/{page_id}/children` でブロック取得
   - テーブルブロックは `/v1/blocks/{table_id}/children` で行データも取得
   - **APIアクセスに失敗した場合**: ユーザーにチケット内容のCSVまたはテキストファイルのパスを確認し、そのファイルから情報を読み込む
2. 以下の情報を抽出する:
   - **KPI一覧**: 集計したいKPIとログ出力有無テーブル
   - **user_action_raw**: 追加・変更・削除されるアクション一覧（action名、detail、対象デバイス、発火領域）
   - **user_log_raw**: 追加・変更・削除されるインプレッションログ一覧
   - **log_action_***: ログアクションの変更有無
   - **その他ログ**: CakePHPアクセスログ、決済ログ、会員登録ログ等の変更有無
   - **refパラメータ**: サービス詳細・ブログ詳細のrefパラメータ追加有無
   - **レビュー状況**: DT室・DAのレビュー済み/未済

### Step 2: 仕様書読み込み

1. user_action仕様書をGoogle Sheets APIで自動取得する
   - スプレッドシートID: `1Zwx5yax-TBXTOkXHFWfV1sZ22my3GhmBQ39K_tN_KSg`
   - シート名: `user_action`、データ範囲: `A8:O`（8行目がヘッダー、行数上限なし）
   - 認証: `gcloud auth application-default print-access-token` でトークン取得
   - ヘッダー: `Authorization: Bearer {token}`, `x-goog-user-project: indigo-medium-816`
   - API: `https://sheets.googleapis.com/v4/spreadsheets/{id}/values/{range}`
   - 主要カラム: B列=大分類, C列=No., D列=小分類, E列=行動, F列=action, G列=詳細情報(detail), I列=PC Web, J列=SP Web, K列=アプリ, M列=Amplitude取り込み有無
   - **APIアクセスに失敗した場合**: ユーザーに仕様書のCSVファイルパスを確認し、そのファイルから読み込む
2. 既存のリソースファイルも参照する:
   - `.claude/resources/coconala/user-action-guide.md` — アクション命名規則・テーブル構成

### Step 3: レビュー実施

以下の観点で各アクションをレビューする:

#### 3-1. 命名規則チェック

- `view_` prefix = 画面表示、`action_` prefix = 操作・実行 の規則に従っているか
- 既存アクション名との**衝突がないか**（仕様書の全635件と照合）
- 既存の類似アクションとの**命名一貫性**があるか
  - 例: 既存が `view_register_input` / `action_register_add` なら、新規も同じ粒度・構造で命名されているか
- view/action の**ペア整合性**: 表示と操作が対になる場合、命名が揃っているか
- **意味が明確か**: 略語や独自用語が含まれる場合、意味がわかるか
- **単数形必須**: アクション名は単数形を使う（複数形は使わない）
- **action_ の末尾は動詞**: `action_` prefix の場合、末尾を動詞にする（例: `action_register_add`、`action_service_edit`）
- **機能名の挿入位置**: `{view|action}_{機能名}_{画面名|操作名}` の構造に従っているか（機能名が正しい位置に入っているか）

#### 3-2. detail設計チェック

- **detailが空欄でないか**: 操作系アクション（action_*_add 等）は分析に必要なIDや属性が必須
- 既存の同種アクションと**detail項目が揃っているか**
  - 例: 既存 `action_register_add` に `type`, `purpose`, `private_corporation` があるなら、新版にも同等の項目が必要
- detail値の**形式が明記されているか**: key名、値域（enum値）、型（数値/文字列/配列）
- **条件付きフィールド**の挙動が明記されているか（条件外の場合: null / false / フィールドなし のどれか）
- `view_id` が必要な箇所に含まれているか

##### 機能種別ごとの必須detail項目

- **検索機能**: 検索条件に加え `result_count`（検索結果件数）が必須
- **サービスID返却**: `impression_service_ids`（表示されたサービスIDの配列）が必須
- **ユーザーID返却**: `impression_user_ids`（表示されたユーザーIDの配列）が必須
- **ブログID返却**: `impression_blog_ids`（表示されたブログIDの配列）が必須
- **購入機能**: 対象ID（service_id等）に加え `order_id` が必須

##### detail値の形式ルール

- **日付**: `YYYY-MM-DD hh:mm:ss` 形式、日本時間（JST）で記録
- **null値**: 値がない場合は `key: null` とする（keyごと省略しない）
- **文字列**: 数値であっても0埋め等がある場合は文字列として扱う（例: `"007"`）
- **数値**: 金額（price）等は数値型で記録する（文字列にしない）
- **真偽値**: `is_XXX` のようなフラグは `true` / `false` で記録する（0/1にしない）

#### 3-3. 出力先チェック

- `action_` prefix のアクションが `user_action_raw` に出力されるか（通常の慣例）
- `user_log_raw`（インプレッションログ）に出力する場合、その理由が明記されているか
- `user_log_raw` 内でも `view_` / `action_` の使い分けルールは同様に適用されるか確認
- 高頻度発火するアクションが `user_action_raw` を肥大化させないか

#### 3-4. 既存アクションとの関係チェック

- 新アクションが既存アクションの**代替**なのか**併存**なのか明記されているか
- 代替の場合、既存アクションの廃止（Amplitude取り込み有無=99化、仕様書グレーアウト）計画があるか
- 併存の場合、分析時の使い分けルールが明確か

#### 3-5. 発火タイミング・デバイス差異チェック

- **発火タイミング**が明確に定義されているか（ボタン押下時 / API成功時 / 画面遷移時 など）
- PC Web / SP Web / アプリ での発火有無が明記されているか
- アプリ固有の注意事項（同時発火、タブ切り替え発火など）が考慮されているか

#### 3-6. KPI整合性チェック

- チケットに記載されたKPIが、追加されるログで実際に集計可能か
- ファネル分析に必要なステップが欠けていないか

#### 3-7. Amplitude投入判断チェック

以下のフローに沿って、各アクションのAmplitude投入要否を判定する。

**判断フロー:**

1. **PM意向の確認**: チケットに「Amplitude連携要否」列があり、PMが「要」or「不要」を明示しているか
   - 未記載の場合 → **要確認**: PMに記入を依頼するよう指摘する
2. **継続性の判断**: このデータを今後も恒常的に見ていくか
   - ABテスト期間限定 → 原則「要」（事業部側でABテストの結果集計・分析ができるようにするため）
   - 一時的な調査のみ → 原則「不要」（BQで十分）
3. **データ量の考慮**: 高頻度発火でAmplitudeのデータ量を圧迫しないか
   - インプレッション系など高頻度発火 → 原則「不要」（BQで分析）
4. **Amplitude利用の必然性**: 以下の向き・不向きに照らして判断する
   - **Amplitude向き → 「要」**
     - ファネル分析（画面遷移率・ステップ間離脱の可視化）
     - N1分析・ユーザーストリーム（個別ユーザーの行動を時系列で追う）
     - セグメント比較（ユーザー属性別の行動比較をGUIで操作）
     - イベント数 or イベント実施UUの集計
     - 開封率など比率系の指標
     - 事業部・PMがSQLなしでセルフサービス分析したいケース
   - **Amplitude不向き → 「不要」（BQで実施）**
     - 複合条件UU（「相談を行ったUU」等、イベント数・イベント実施UU以外のKPI）
     - 正確な金額集計（流通高・売上）— キャンセル・ポイント併用・銀振未払いの扱いでBQと差異が出る
     - 複数テーブルのJOINが必要な分析
     - 当日リアルタイム集計（Amplitudeは1日遅れ）
5. **既存アクションとの整合**: 同種の既存アクションのAmplitude取り込み有無（1 or 99）と揃っているか

**補足ルール:**
- 代替アクションを投入する場合、旧アクションの取り込み有無を `99` に変更する計画があるか確認
- bot除外済みデータで投入すること（Amplitude側での除外はデータ量を浪費する）

**判定結果:** 各アクションについて以下のいずれかを出力する
- `1`（投入要）: 恒常KPI or ABテスト用 + 低〜中頻度 + Amplitudeの分析機能が活きる
- `99`（投入不要）: 一時的な調査のみ or 高頻度 or BQで十分
- `要確認`: PM意向が不明、または判断が分かれるケース

#### 3-8. 運用面チェック（※レビュー対象外）

> 以下の項目はレビュー結果には含めない。参考情報として記載のみ。

- 仕様書の**担当者・更新日付**が記入されているか
- 仕様書への**転記計画**があるか（No.636以降への追記）
- **レビュー状況**: DT室・DA両方のレビューが必要

### Step 4: レビュー結果出力

以下のフォーマットで結果を出力する:

```markdown
## ログ出力チケット レビュー結果

### チケット概要
- タイトル: {タイトル}
- 追加アクション数: N件
- 変更アクション数: N件
- 削除アクション数: N件

### レビュー結果サマリ

| アクション名 | 判定 | 指摘数 | Amplitude投入 |
|---|---|---|---|
| action_xxx | 要修正 / 要確認 / OK | N件 | 1（要） / 99（不要） / 要確認 |

### 詳細指摘事項

#### {action_name}

| # | 重要度 | 観点 | 内容 |
|---|---|---|---|
| 1 | 要修正 / 要確認 / 軽微 / OK | 命名規則 / detail設計 / 出力先 / 既存関係 / 発火タイミング / KPI整合性 / Amplitude投入 | 具体的な指摘内容 |

### まとめ（対応優先度順）
1. ...
2. ...
```

## 重要度の定義

| 重要度 | 意味 |
|---|---|
| 要修正 | このままリリースすると分析に支障が出る。修正必須 |
| 要確認 | 意図的な設計かもしれないが、確認が必要 |
| 軽微 | あった方がよいが、なくてもリリース可能 |
| OK | 問題なし |
