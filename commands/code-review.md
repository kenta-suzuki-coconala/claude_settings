# 共感的コードレビュー

## 目的
開発者に寄り添いながら建設的なコードレビューを行い、コード品質向上をサポートします。技術的な指摘だけでなく、良い点も積極的に評価し、学習と成長を促進します。

## 実行内容

### ステップ1: コード分析
- 指定されたファイル/ディレクトリのコードを読み取り
- コード構造と実装パターンを理解
- 関連するテストファイルの存在確認

### ステップ2: SOLID原則評価
- **Single Responsibility Principle（単一責任原則）**: クラス・関数の責任範囲
- **Open/Closed Principle（オープン・クローズド原則）**: 拡張性と変更耐性
- **Liskov Substitution Principle（リスコフの置換原則）**: 継承関係の適切性
- **Interface Segregation Principle（インターフェース分離原則）**: インターフェースの設計
- **Dependency Inversion Principle（依存関係逆転原則）**: 依存関係の方向性

### ステップ3: テスト品質評価
- テストケースの網羅性
- テストの可読性と保守性
- モックやスタブの適切な使用
- エッジケースのカバレッジ
- テストの実行速度と安定性

### ステップ4: 共感的レビュー出力
- **良い点の積極的評価**: 優れた実装やアプローチを具体的に褒める
- **改善提案**: 建設的で実行可能な改善案を優しい口調で提示
- **学習リソース**: 関連する学習材料やベストプラクティスの紹介
- **優先度付け**: 重要度に応じた改善項目の整理

## パラメータ
- **$1**: レビュー対象のファイルパスまたはディレクトリパス
- **$ARGUMENTS**: 複数ファイル指定時の全パス

## 使用例
```
/user:code-review src/components/UserService.ts
/user:code-review src/services/
/user:code-review tests/unit/user.test.ts src/models/User.ts
```

## レビュー出力形式

### 🌟 素晴らしい点
- 良い実装やアプローチを具体的に評価

### 🔍 SOLID原則の評価
- 各原則に対する評価と具体例

### 🧪 テスト品質の評価
- テストの現状と改善点

### 💡 改善提案
- 優先度付きの建設的な提案

### 📚 学習リソース
- 関連する参考資料やベストプラクティス

---

**注意**: このレビューは建設的な成長支援を目的としています。すべての指摘は学習機会として捉え、段階的な改善を心がけてください。

## 実装ロジック

指定されたパス（$1）に対して以下の処理を実行：

1. ファイル/ディレクトリの存在確認
2. 対象ファイルの読み取り（.ts, .js, .py, .java, .go等）
3. 関連テストファイルの検索と読み取り
4. SOLID原則に基づく構造分析
5. テスト品質の多角的評価
6. 共感的で建設的なフィードバックの生成
7. 日本語での丁寧な出力

レビュー対象が見つからない場合は、適切なエラーメッセージを日本語で出力します。
